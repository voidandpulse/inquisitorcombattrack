# Inquisitor's Combat Log

A damage calculator for a single Pathfinder 1e character: a level 16
half-elf Inquisitor (Sworn of the Eldest), sworn to a homebrew fae Eldest.

It exists because her damage is a fistful of d6s. Weapon dice, 4d6 of greater
bane, 2d6 holy, mage strike scaling, and a bard who hands out numbers mid-round
— enough dice on the table that resolving one full attack took longer than the
rest of the turn. This does the arithmetic. It deliberately does **not** roll
attack rolls; those stay on actual dice.

There are two builds, both single self-contained HTML files:

| file | dice | needs |
|---|---|---|
| `combat-log-3d.html` | full set, d4 to d20, rendered in WebGL | three.js and cannon-es from a CDN |
| `strikes.html` | d6 only, rendered in CSS | nothing at all |

Open either in a browser. `combat-log-3d.html` is the current one; `strikes.html`
is kept because it has no dependencies and still works offline.

## What it does

- **Per-damage-type breakdown.** Totals are split by type — physical, holy,
  fire, untyped — so DR and energy resistance can be applied at the table. The
  tool doesn't do the DR math, it just makes clear what's exposed to it and
  what bypasses it.
- **Bonus-type stacking.** Pathfinder suppresses all but the largest bonus of a
  given type. Suppressed sources are still listed, greyed, with the number they
  would have contributed, so it's visible *why* a buff did nothing.
- **Action economy.** Each option is labelled free / swift / immediate /
  standard.
- **Criticals.** Only the dice that actually multiply are multiplied — weapon
  dice and static bonuses — while holy, bane, energy and Decapitate are added
  once, after.

### Bonus resolution

Every bonus goes into a pool keyed by type. Within a type the largest value
applies and the rest are flagged suppressed; a tie pays out once. Untyped
bonuses all stack. That rule is `resolve()` in the first inline script, and
`tests/bonus-pool.js` lifts it straight out of the HTML and tests it, so the
test can't drift away from the implementation.

## The dice

Rolls are shown as tumbling 3D dice, coloured per source, because automated
results arrive faster than hand-rolled ones and the anticipation was worth
keeping. Each damage source gets its own colour (bane rolls in `#9E004F`).

### The current build

`combat-log-3d.html` uses [three.js][t] to draw and [cannon-es][c] for the
motion. The solids are defined once as vertices and faces, and that one
definition drives all three uses: three triangulates it into a mesh, cannon-es
builds the collision hull from it, and the result is read from its face normals.
Getting it wrong is therefore wrong everywhere at once, so the geometry is
checked rather than eyeballed — `tests/shape-validate.js` asserts that every
face is planar, every normal points outward, every solid is convex, opposite
faces sum to one more than the number of sides, and every face sits the same
distance from the centre. That last property, face-transitivity, is what makes
a die fair: each face is equally stable to rest on.

Three things that check caught, none of them visible in a render:

1. The d10's kite faces were not planar. A pentagonal trapezohedron only closes
   for one ratio of apex height to ring offset, which has to be solved for
   (0.10557) rather than guessed at.
2. Face values were being paired against inward-pointing normals, because the
   numbering ran before the winding fix. Opposite faces summed to 9 and 14
   instead of 11.
3. The rounded d6's UVs were transformed once per index-buffer entry rather
   than once per vertex, so shared vertices were mapped twice and every face
   came out blank.

A d4 is read at its apex, not its upper face, because a resting tetrahedron
points a vertex at the ceiling. It carries three numerals per face, like a real
one.

### The dependency-free build

`strikes.html` carries a small rigid-body simulation written for this project —
a cube with eight corner contacts, impulse resolution with Coulomb friction,
quaternion integration, sleep detection — rendered with CSS `matrix3d` rather
than WebGL. It rolls d6s only.

It was tested the same way, and the first two versions failed:

1. Random starting orientations were generated by normalising four independent
   uniforms, which clusters in one octant of rotation space instead of covering
   it evenly. Replaced with Shoemake's method.
2. More seriously, the solver resolved the eight corner contacts in a **fixed
   order in the die's own frame**, so the same local corners always won the
   argument. Every face lost to its opposite. Shuffling the contact order each
   step fixed it.

Neither was visible by reading the code. Both were found by rolling several
thousand dice and running a chi-square test.

### Results

Every chi-square below is reported with the effect size the sample can actually
detect, so a clean number is not mistaken for a tighter bound than the data
supports.

| dice | rolls | chi-square | p | worst face off by |
|---|---|---|---|---|
| CSS solver, d6 | 100,000 | 6.23 (5 df) | 0.29 | 0.22 pt |
| cannon-es, d6 | 100,000 | 3.69 (5 df) | 0.60 | 0.15 pt |
| cannon-es, d10 | 21,000 | 3.94 (9 df) | 0.92 | 0.28 pt |
| cannon-es, d4/d6/d8/d12/d20 | 3,000 each | — | 0.13 to 0.62 | under 1.5 pt |

`tests/compare-engines.js` runs the first two side by side under matched
constants, launch distribution, timestep and face-reading code, so the only
difference between those rows is the solver. Both are ordinary draws from the
same null distribution: this is not evidence that either is fairer, only that
neither shows a bias above about four tenths of a percentage point. The reason
to prefer the library build is dice shapes beyond a cube, not fairness.

[t]: https://threejs.org
[c]: https://github.com/pmndrs/cannon-es

## Tests

```
node tests/bonus-pool.js        # bonus-type stacking and suppression
node tests/shape-validate.js    # geometry of every solid in the 3D build
node tests/dice-fairness.js     # rolls the CSS solver, chi-square on faces
node tests/face-reading.js      # isolates "which face is up" from the physics

npm install                     # cannon-es, needed only for the next two
node tests/shape-fairness.js    # every shape, d4 to d20, dropped and counted
node tests/compare-engines.js   # the CSS solver against cannon-es, side by side
```

`dice-fairness.js` and `face-reading.js` split the problem deliberately: if the
reading test is clean and the fairness test is not, the bias is in the solver.
That is how the contact-ordering bug was localised. Each takes an optional
sample count as the first argument.

Every test reads the HTML it is testing and lifts the real code out of it, so a
test cannot drift away from the implementation it is supposed to be checking.
All of them exit non-zero on failure and run in CI unchanged.

## Scope

This is built around one character's sheet, not a general Pathfinder
calculator. Bonuses that are static for it are baked in; the ones that vary
round to round are inputs. Known gap: the bard's mythic inspire competence and marked-target bonuses are
entered by hand rather than toggled.

## How it was built

Written with Claude as a pair. The division of labour was the interesting part:
the model wrote the physics and the Pathfinder bookkeeping, but the bug that
mattered — a single unquoted attribute selector, `[data-sw=1]`, which is
invalid CSS and threw at load, silently killing every handler defined after it
— survived three rewrites and was only found by opening the file locally and
reading the console. The dice fairness bugs went the other way: invisible to
inspection, caught by statistics.
