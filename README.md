# Sidra's Combat Log

A damage calculator for a single Pathfinder 1e character: Sidra, a level 16
half-elf Inquisitor (Sworn of the Eldest), sworn to Nyrissa.

It exists because her damage is a fistful of d6s. Weapon dice, 4d6 of greater
bane, 2d6 holy, mage strike scaling, and a bard who hands out numbers mid-round
— enough dice on the table that resolving one full attack took longer than the
rest of the turn. This does the arithmetic. It deliberately does **not** roll
attack rolls; those stay on actual dice.

Open `strikes.html` in a browser. One file, no build step, no dependencies.

## What it does

- **Per-damage-type breakdown.** Totals are split by type — physical, holy,
  fire, untyped — so DR and energy resistance can be applied at the table. The
  tool doesn't do the DR math, it just makes clear what's exposed to it and
  what bypasses it.
- **Bonus-type stacking.** Pathfinder suppresses all but the largest bonus of a
  given type. Suppressed sources are still listed, greyed, with the number they
  would have contributed, so it's visible *why* a buff did nothing.
- **Action economy.** Each option is labelled free / swift / immediate /
  standard.
- **Criticals.** Only the dice that actually multiply are multiplied — weapon
  dice and static bonuses — while holy, bane, energy and Decapitate are added
  once, after.

### Bonus resolution

Every bonus goes into a pool keyed by type. Within a type the largest value
applies and the rest are flagged suppressed; a tie pays out once. Untyped
bonuses all stack. That rule is `resolve()` in the first inline script, and
`tests/bonus-pool.js` lifts it straight out of the HTML and tests it, so the
test can't drift away from the implementation.

## The dice

Rolls are shown as tumbling 3D dice, coloured per source, because automated
results arrive faster than hand-rolled ones and the anticipation was worth
keeping. Each damage source gets its own colour (bane rolls in `#9E004F`).

The physics is a small rigid-body simulation written for this — a cube with
eight corner contacts, impulse resolution with Coulomb friction, quaternion
integration, sleep detection — rendered with CSS `matrix3d` rather than WebGL.

It is tested for fairness rather than assumed fair, because the first two
versions were not:

1. Random starting orientations were generated by normalising four independent
   uniforms, which clusters in one octant of rotation space instead of covering
   it evenly. Replaced with Shoemake's method.
2. More seriously, the solver resolved the eight corner contacts in a **fixed
   order in the die's own frame**, so the same local corners always won the
   argument. Every face lost to its opposite. Shuffling the contact order each
   step fixed it.

Neither was visible by reading the code. Both were found by rolling several
thousand dice and running a chi-square test, which is what `tests/` does.

Current result, at 100,000 reads: chi-square 6.23 (5 df, p = 0.29), mean 3.496,
no face off true by more than 0.22 percentage points, no roll failing to settle.
That run has roughly 80% power against a single face landing 17.1% of the time
instead of 16.7%, so the claim it supports is "no face is off by more than about
four tenths of a point."

`tests/compare-engines.js` runs the same test against [cannon-es][c], a
published rigid-body engine, under matched constants, launch distribution,
timestep and face-reading code, so the only difference between the two columns
is the solver. At 100,000 reads each, cannon-es scored chi-square 3.69
(p = 0.60) and this project's solver 6.23 (p = 0.29) -- both ordinary draws
from the same null distribution, and not evidence that either is fairer. The
reason to prefer a library here would be dice shapes beyond a cube, not
fairness.

[c]: https://github.com/pmndrs/cannon-es

## Tests

```
node tests/bonus-pool.js      # bonus-type stacking and suppression
node tests/dice-fairness.js   # rolls the shipped physics, chi-square on faces
node tests/face-reading.js    # isolates "which face is up" from the physics

npm install                   # cannon-es, needed only for the next one
node tests/compare-engines.js # this solver against cannon-es, side by side
```

`dice-fairness.js` and `face-reading.js` split the problem deliberately: if the
reading test is clean and the fairness test is not, the bias is in the solver.
That's how the contact-ordering bug was localised. Both take an optional sample
count as the first argument.

All of them read `strikes.html` directly and exit non-zero on failure, so they can
run in CI unchanged.

## Scope

This is built around one character's sheet, not a general Pathfinder
calculator. Bonuses that are static for Sidra are baked in; the ones that vary
round to round are inputs. Known gaps: the bard's mythic inspire competence and
marked-target bonuses are entered by hand rather than toggled, and Spiritual
Weapon needs a d8 the physics tray doesn't have yet, so it falls back to a
simpler tumble.

## How it was built

Written with Claude as a pair. The division of labour was the interesting part:
the model wrote the physics and the Pathfinder bookkeeping, but the bug that
mattered — a single unquoted attribute selector, `[data-sw=1]`, which is
invalid CSS and threw at load, silently killing every handler defined after it
— survived three rewrites and was only found by opening the file locally and
reading the console. The dice fairness bugs went the other way: invisible to
inspection, caught by statistics.
